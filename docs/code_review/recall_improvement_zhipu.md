# 招投标法规智能问答系统召回率优化分析报告

## 问题诊断

### 1. 同义词改写问题导致82.5%的miss

**根本原因：**
- 当前Query Rewrite层禁用了同义词扩展，仅保留口语→书面语转换和法条号规范化
- 但评测数据显示，82.5%的miss来自synonym类型问题，说明用户查询与文档表达存在大量同义差异
- BM25检索依赖关键词匹配，缺乏同义词扩展导致召回严重不足

**证据：**
- Miss样本中，如"市交易中心每日更新信用记分的方式是什么？"与"市交易中心每日更新对响应方的信用记分"存在表达差异
- "该业务规范的执行时间和有效期分别是多久？"与"本规范自2020年12月1日起施行，有效期至2025年11月30日"表达不一致

### 2. pdf_law_child召回率低，Parent expansion零贡献

**根本原因：**
- 法条子片段(chunk)被过度切分，导致关键信息分散
- Parent Context Expander当前只对chunk_type="child"的结果进行扩展，但实际数据中pdf_law_child占比21.4%，且多为法条子部分
- 扩展器依赖parent_id字段，但可能存在数据质量问题导致无法正确关联parent

**证据：**
- Miss样本中，如"《中华人民共和国刑法》第二百二十三条第一款规定的内容是什么？"未能命中对应法条
- Parent expansion后recall没有提升，说明扩展机制未生效

### 3. Weighted Fusion效果不佳

**根本原因：**
- 融合策略过于复杂，引入过多动态调整反而可能引入噪声
- BM25和Dense的权重分配可能不合理，尤其是法规实体检测的判断逻辑
- Min-Max归一化可能不适合不同分布的分数

**证据：**
- Fusion后recall仅从70.6%提升到71.0%，提升微乎其微
- 动态权重调整可能没有真正解决不同类型查询的需求差异

### 4. 单chunk可答问题占miss的61.5%

**根本原因：**
- 查询表达与文档内容存在语义鸿沟，关键词匹配失效
- 检索粒度可能不合适，chunk过大或过小都影响召回
- 预处理阶段可能丢失了关键信息

**证据：**
- Miss样本中，如"招标公告或者投标邀请书应当载明哪些事项？"未能命中对应法条
- 这些问题理论上应该很容易命中，但实际表现最差

### 5. Expected chunk与top1 chunk的差异规律

**分析发现：**
1. **表达差异**：用户口语化表达与文档正式表述不一致
   - 用户问"市交易中心每日更新信用记分的方式"，文档表述"市交易中心每日更新对响应方的信用记分"
   
2. **信息缺失**：用户查询包含文档中没有的词语
   - 用户问"该业务规范的执行时间和有效期"，但文档中只有"本规范自2020年12月1日起施行，有效期至2025年11月30日"

3. **上下文依赖**：答案需要跨chunk理解
   - 用户问"评标委员会发现投标文件不明确、有错误的内容应如何处理？"，答案分散在多个chunk中

4. **法条引用不准确**：用户引用法条号与实际文档不一致
   - 用户问"《中华人民共和国刑法》第二百二十三条第一款"，但实际内容在另一文档中

## 优化建议

### 1. 重新启用并优化同义词扩展（优先级：最高）

**具体方案：**
- 重新启用Query Rewrite中的同义词扩展功能，但采用更智能的策略
- 建立招投标领域专用同义词词典，包含：
  - 官方术语与口语表达对应关系（如"招标人"vs"业主"）
  - 行业习惯用语与标准术语对应关系（如"围标"vs"串通投标"）
  - 动态同义词发现机制，基于用户查询-文档匹配结果自动扩充

**实施步骤：**
1. 收集用户查询与文档表达差异的典型案例，构建初始同义词词典
2. 在Query Rewrite阶段，对非定义类问题进行同义词扩展
3. 在BM25检索时，对扩展后的查询进行多路检索，避免语义漂移

**预期效果：**
- 可解决约80%的synonym类型miss问题
- 预期整体Recall@5可提升5-8个百分点

### 2. 优化法条子片段检索策略（优先级：高）

**具体方案：**
- 改进chunk粒度控制，对法条类文档采用更合理的分割策略
- 增强Parent Context Expander：
  - 不再依赖chunk_type标记，而是基于content特征自动识别法条子部分
  - 建立法条层级关系索引，支持多级上下文扩展
  - 实现法条号到法条内容的精确映射

**实施步骤：**
1. 重新处理法条类文档，采用"章-节-条"三级结构化分割
2. 为每个法条子部分添加article_id和层级关系元数据
3. 扩展Parent Context Expander，支持向上扩展到完整法条和章节上下文

**预期效果：**
- 解决pdf_law_child类型问题，提升法条类文档召回率
- 预期法条相关问题的Recall@5可提升10-15个百分点

### 3. 简化并优化融合策略（优先级：中）

**具体方案：**
- 简化Weighted Fusion逻辑，减少动态调整的复杂性
- 采用RRF(Reciprocal Rank Fusion)作为主要融合策略，配合简单权重调整
- 基于查询类型和结果质量动态调整融合参数，而非基于查询内容预测

**实施步骤：**
1. 实现RRF融合算法作为基础
2. 添加简单的查询类型分类（如定义类、流程类、条件类）
3. 根据历史反馈数据，为不同查询类型设置最优融合权重

**预期效果：**
- 提高融合稳定性，减少噪声引入
- 预期Recall@5可提升2-4个百分点

### 4. 增强查询理解与表达匹配（优先级：中）

**具体方案：**
- 实现查询意图识别，针对不同意图采用不同检索策略
- 建立查询-文档表达映射模型，解决表达差异问题
- 引入语义检索作为补充，解决关键词匹配失效问题

**实施步骤：**
1. 训练查询意图分类器，识别定义查询、流程查询、条件查询等
2. 构建查询-文档表达映射词典，解决常见表达差异
3. 在Dense Retrieval中引入语义相似度计算，增强语义匹配能力

**预期效果：**
- 解决单chunk可答问题中的表达差异
- 预期Recall@5可提升3-5个百分点

### 5. 引入主动学习与反馈机制（优先级：低）

**具体方案：**
- 建立用户反馈机制，收集实际miss案例
- 基于反馈数据持续优化检索策略和同义词词典
- 实现A/B测试框架，验证不同优化策略的效果

**实施步骤：**
1. 在系统中添加反馈入口，允许用户标记检索结果质量
2. 定期分析反馈数据，识别系统性问题
3. 建立模型迭代优化流程，持续改进系统性能

**预期效果：**
- 长期持续提升系统性能，形成良性循环
- 预期每轮迭代可提升1-2个百分点Recall@5

## 总结

当前系统的主要问题在于查询表达与文档内容之间的语义鸿沟，以及法条类文档的检索策略不当。通过重新启用并优化同义词扩展、改进法条子片段检索策略、简化融合策略等措施，预计可以将Recall@5从当前的82.0%提升至90%以上。建议优先实施前两项高优先级改进，预计可以解决大部分miss问题。
