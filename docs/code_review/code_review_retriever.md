### ① Recall下降原因分析

**核心问题：查询改写过度导致语义漂移**
1. **口语转书面语过度替换**（`query_rewriter.py`）
   - 单字词替换依赖jieba分词，边界不清晰（如"交易"→"提交易"）
   - 同义词扩展未考虑领域歧义（如"围标"→"串通投标"可能改变用户意图）
   - 冗余去除可能删除关键上下文（如"我想问一下"包含用户意图线索）

2. **融合策略缺陷**（`fusion.py`）
   - RRF的k值（60）过大，稀释了高质量结果
   - WeightedFusion的动态权重（0.65/0.35）未考虑不同集合特性
   - Boost/Penalty规则过于简单（仅关键词匹配+chunk_type）

3. **Parent Context扩展问题**（`expanders.py`）
   - 新旧路径（chapter_context vs child→parent）合并逻辑混乱
   - 缓存未及时更新，可能返回过期数据

4. **精排引入噪声**（`rerankers.py`）
   - 远程Rerank不稳定时fallback到本地，模型不一致
   - 精排候选池（RERANK_POOL=30）可能遗漏重要结果

---

### ② Hybrid设计问题

**核心问题：融合策略缺乏自适应能力**
1. **固定权重分配**（`fusion.py`）
   ```python
   # 当前硬编码权重
   return (0.75, 0.25)  # keyword_heavy
   return (0.40, 0.60)  # semantic_heavy
   ```
   - 未考虑不同集合（regulations vs bids）的特性差异
   - 未根据历史查询效果动态调整

2. **RRF与WeightedFusion割裂**
   - 两种策略通过配置选择，无法根据查询特性自动切换
   - 缺乏融合效果评估机制

3. **Boost规则过于简单**
   - 仅基于关键词出现和chunk_type，未考虑：
     - 查询与结果的语义相似度
     - 结果的权威性（如法规层级）
     - 用户历史偏好

---

### ③ Rewrite设计问题

**核心问题：规则化改写缺乏语义理解**
1. **同义词扩展歧义**（`preprocessor.py`）
   ```python
   SYNONYMS = {
       "围标": ["串标", "串通投标"],  # 可能改变用户原始意图
       "资质": ["资格", "资信"],     # 领域内含义有差异
   }
   ```
   - 未区分同义词的语义强度
   - 扩展后未验证语义一致性

2. **冗余去除粗暴**
   - 删除"请问"、"我想知道"等礼貌用语可能丢失用户意图
   - 未考虑上下文重要性（如"这个"可能指代前文内容）

3. **条款号规范化缺陷**
   - 仅处理"第X条"，未覆盖"第X款"、"第X项"等变体
   - 中文数字转换未考虑"百"、"千"等大数（如"第一百二十三条"）

---

### ④ Parent Context问题

**核心问题：上下文扩展逻辑混乱**
1. **新旧路径冲突**（`expanders.py`）
   ```python
   # 新旧路径并行处理，可能导致重复或遗漏
   if chapter_context:
       # 新路径：章上下文直接注入
   elif str(meta.get("chunk_type", "")).endswith("_child"):
       # 兼容路径：旧child chunk → 查找parent
   ```
   - 同一chunk可能被新旧路径同时处理
   - 缺乏优先级机制（如优先使用chapter_context）

2. **缓存更新滞后**
   - `ParentContextExpander`的缓存机制未与数据更新同步
   - 可能返回过期的parent_content

3. **上下文过长问题**
   - 注入的parent_content可能稀释关键信息
   - 未对上下文长度进行截断或摘要

### ⑤ RRF是否合理

**核心问题：参数设置不合理**
1. **k值过大**（`fusion.py`）
   ```python
   RRF_K = 60  # 当前值过大
   ```
   - 导致低质量结果过度参与融合
   - 建议调整为10-20

2. **未考虑检索器置信度**
   - RRF平等对待Vector和BM25结果
   - 未根据历史查询效果动态调整两路结果的权重

3. **缺乏融合效果评估**
   - 无法判断RRF是否优于WeightedFusion
   - 缺乏A/B测试机制

---

### ⑥ Rerank是否合理

**核心问题：精排策略不稳定**
1. **远程服务依赖风险**（`rerankers.py`）
   ```python
   if self._use_remote:
       try:
           ranked = self._try_remote_rerank(...)  # 远程优先
       except Exception:
           self._use_remote = False  # 失败后禁用远程
   ```
   - 远程服务不可用时直接禁用，无降级策略
   - 本地模型加载延迟影响响应速度

2. **候选池设置不合理**
   - RERANK_POOL=30可能遗漏重要结果
   - 未根据查询类型动态调整候选池大小

3. **文本选择问题**
   - 精排时使用parent_content可能过长
   - 未针对不同chunk类型优化文本选择策略

---

### ⑦ Query Routing建议

**核心问题：路由策略缺乏动态性**
1. **BinaryRouter三路投票缺陷**（`router.py`）
   ```python
   # 规则+Embedding+LLM投票，但未考虑投票权重
   votes = [rule_is_sql, embedding_is_sql, llm_is_sql]
   is_sql = sum(valid) >= len(valid) / 2  # 简单多数
   ```
   - 未根据各路由器历史准确率调整投票权重
   - LLM投票失败时自动弃票，可能降低准确性

2. **路由器选择僵化**
   - 通过配置文件静态选择路由器
   - 无法根据查询特性动态切换（如简单问题走BinaryRouter，复杂问题走PlannerRouter）

3. **SQL模板匹配阈值问题**
   ```python
   TEMPLATE_MATCH_THRESHOLD = 0.92  # 过高导致召回不足
   ```
   - 阈值过高导致模板匹配召回率低
   - 未考虑查询与模板的语义相似度

### ⑧ 工程隐患

**核心问题：系统健壮性不足**
1. **缓存一致性问题**
   - `BM25Retriever`和`ParentContextExpander`的缓存未与数据更新同步
   - 可能返回过期或错误数据

2. **并发安全问题**
   - `EmbeddingService`和`BgeReranker`的本地模型加载存在竞争条件
   - 多线程环境下可能出现模型重复加载

3. **外部服务依赖风险**
   - 远程Embedding/Rerank服务不可用时系统降级能力不足
   - 缺乏服务健康检查和自动切换机制

4. **错误处理不完善**
   - 检索管线的断路器机制可能掩盖错误
   - 关键阶段失败时缺乏详细日志记录
