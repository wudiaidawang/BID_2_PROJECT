## 四、你观察到的现象：解释

> "一开始舆情以文章为父、文段为子，法规以款为父以条为子，中间做测试渐渐这些设置不见了"

**对，这是 V4.2 的刻意变更。** 原因分析：

### 原来的设计 (V1-V3)
```
法规 PDF
  │
  ▼
款 (subsection) ← Parent Chunk
  │  e.g. "第三十七条 投标人不得..."
  ├── 条 (clause 1) ← Child Chunk
  ├── 条 (clause 2) ← Child Chunk
  └── 条 (clause 3) ← Child Chunk

检索: query → 命中 child → 展开 parent → 获取完整条款上下文
```

### V4.2 改为
```
法规 PDF
  │
  ▼
完整条款 (article) ← Parent Chunk (即原来的 child)
  e.g. "第三十七条 投标人不得... (完整段)"
  
上下文: chapter_context (整章拼接)
  e.g. "第三章 投标 第三十七条... 第三十八条... 第三十九条..."

不再有 child 切分
```

### 为什么这样改

1. **法条太短拆了反而有害**：一条法规条款本身可能只有 1-2 句话，再拆成 child 后语义不完整，embedding 质量差
2. **child→parent 查找引入了额外延迟**：每次检索后还要查一次 parent
3. **chapter_context 提供了更大的上下文**：比单个 parent 条款更完整
4. **评测数据支持**：完整条款做检索单元的召回率明显高于拆分的 child chunk

### 但问题也随之而来

1. **chapter_context 可能过长**：一整章拼接可能数千字，reranker 截断 1024 后后半部分丢失
2. **跨章节的关联信息丢失**：如果正确答案在第三章，但 query 相关的上下文在第四章
3. **article_id 去重过于激进**：同一条款下不同段落共享 article_id，第一个命中后其余全部丢弃（你评测中已发现，R@5 从 53.4% 跌到 7.5%）
4. **policy_doc 和 opinion_news 没有 parent 结构**：它们是扁平文档，没有 chapter_context 可注入，导致这类 chunk 在 parent_content 优先级排序中吃亏

## 五、当前 Query Rewrite 的真实状态

很多人（包括我一开始）以为 query rewrite 在工作，实际上：

```
config.yaml:
  qr_colloquial_to_formal: false   ← 关闭
  qr_redundancy_removal: false     ← 关闭
  qr_synonym_expansion: false      ← 关闭

实际生效的只有:
  ✅ 标点规范化 (常驻)
  ✅ 条款号规范化 (第X条 → 第N条) (常驻)

但 preprocessor.py 里还有一段"同义词扩展-BM25"是硬编码开启的:
  ✅ 定义类跳过
  ✅ 其余直接拼接同义词到 query 文本
  (这部分不受 config.yaml 控制)
```

这就解释了为什么 V6 评测中预处理仍在影响召回——preprocessor 的同义词拼接绕过了 config 的开关。
